# 对 4 个确认问题的回复

## 1. `loadMessagesFromPi()` 和 `reloadMessagesFromPi()` 是否共存？

**确认：应该共存。**

现有 `loadMessagesFromPi()` 是 append 语义：它从 Pi `get_messages` 拉消息，然后逐条 `this.messages.push(msg)` 和 `this.renderMessage(msg)`，没有先清空当前消息列表。([GitHub][4])

这个方法可以保留，用于当前已有流程，避免大范围破坏。但是 rewind / return / switch 之后，应该使用新的：

```ts
reloadMessagesFromPi()
```

语义是：

```text
clear messages
→ get_messages
→ rebuild UI
→ syncForkEntryIds
```

原因是 rewind 和 return 是 session 状态切换，不能继续 append，否则容易出现旧消息残留或重复消息。

最终决定：

```text
保留 loadMessagesFromPi()：原有 append 逻辑，不大改。
新增 reloadMessagesFromPi()：专门用于 rewind / return / 强制重载。
```

---

## 2. `renderReturnBanner()` 放哪里？

**确认：不要放在 `messagesContainer` 底部。应该放在顶部，全局状态区。**

因为 `Return to latest` 表示的是：

```text
当前正在查看 rewind fork
```

它不是一条 message，而是整个 session view 的状态。放在 messages 底部，用户不一定能看到，尤其历史消息很多时体验不好。

当前代码里 `readOnlyBanner` 是插入到 `inputContainer` 前面，也就是靠近底部；这对只读提示勉强可以，但对 rewind 状态不够明显。([GitHub][4])

更好的结构是：

```text
headerBar
returnBanner
chatBody
inputContainer
```

所以实现上建议给 `chatBody` 增加一个字段：

```ts
private chatBodyEl: HTMLElement | null = null;
```

在 `onOpen()` 里：

```ts
this.chatBodyEl = container.createDiv({ cls: "pi-chat-body" });
```

然后 `renderReturnBanner()` 时插入到 `chatBodyEl` 前面：

```ts
this.contentEl.insertBefore(this.returnBannerEl, this.chatBodyEl);
```

最终决定：

```text
Return banner 放在 headerBar 下方、messages 区域上方。
不放在 messagesContainer 里面。
```

## 3. `returnCheckpoint` 是否持久化？

**确认：第一版不持久化。重启后消失是预期行为。**

`returnCheckpoint` 的本质不是业务数据，而是临时 UI 导航状态：

```ts
returnCheckpoint = {
  originalSessionPath,
  forkSessionPath?,
  createdAt,
}
```

它只服务于这个场景：

```text
用户刚点击 rewind
但还没有发送新消息
所以允许 Return to latest
```

一旦用户关闭 Obsidian、插件重载、切换 session、发送新消息，这个临时状态都应该失效。

不持久化的好处是实现简单、不会产生 stale session path 问题。因为 Pi 的 `fork` 会创建新的 session file，`switch_session` 又依赖具体 sessionPath；如果持久化，就必须处理原 session 被删除、移动、重命名、Pi session dir 改变等边界，第一版没有必要。Pi RPC 文档确认 `switch_session` 是按 `sessionPath` 加载 session 文件，`fork` 是从 active branch 的历史 user message 创建新 fork 并返回原 prompt 文本。([Pi Coding Agent][6])

最终决定：

```text
returnCheckpoint 只保存在内存中。
Obsidian 重启后 Return to latest 消失。
这是第一版预期行为。
```

## 4. `get_fork_messages` 数量不匹配怎么办？

**确认：默认只 `console.warn`，不要 `Notice` 打扰用户。**

Pi RPC 的 `get_fork_messages` 返回的是可 fork 的 user messages，每条包含 `entryId` 和 `text`。([Pi Coding Agent][6])

插件本地 `messages` 里的 user message 可能包括：

```text
steering message
attachment display text
image attached marker
本地缓存恢复的旧消息
read-only saved session message
```

所以数量不完全匹配是可能的。

第一版处理策略应该是：

```text
按顺序尽力绑定。
绑定成功的 user message 显示 rewind 图标。
绑定失败的 user message 不显示图标。
数量不匹配只 console.warn，不 Notice。
```

只有在用户真的点击了某条没有 `piEntryId` 的消息时，才给 Notice：

```text
This message is not rewindable yet.
```

这样不会把内部映射细节暴露给普通用户。

最终决定：

```text
数量不匹配：console.warn。
单条无法 rewind：点击时 Notice。
整体不弹 Notice。
```

# 需要补充的一点：可以支持任意历史 user message，不只是上一个

这个方案不是只能撤销上一步。Pi RPC 的 `fork` 明确是从 active branch 上的 previous user message 创建 fork，`get_fork_messages` 返回多条可 fork 的 user messages，每条都有自己的 `entryId`。([Pi Coding Agent][6])

所以 UI 上可以对每一条绑定成功的 user message 都显示 rewind 图标。

语义是：

```text
点击任意历史 user message
→ fork 到这条 user message 之前
→ 把这条原 prompt 放回输入框
→ 用户可以修改后重新发送
```

但这仍然不是严格 tree undo/redo。严格跨分支任意节点导航要用 extension 里的 `ctx.navigateTree()`，它不是当前 RPC 的直接命令。Pi extension 文档里 `ctx.fork()` 支持 `position: "before"` 和 `position: "at"`，`ctx.navigateTree()` 才是导航到 session tree 另一个 entry 的能力。([Pi Coding Agent][7])

# 最终实现决策

可以按你的调研继续做，最终决策如下：

```text
1. message-types.ts
   - 保留 piEntryId
   - 增加 canRewind?: boolean
   - 增加 piForkText?: string

2. renderer.ts
   - 给 renderUserMessage 增加 actions 参数
   - 在 label 行加 rewind 图标
   - 不改变 assistant/tool 渲染逻辑

3. view.ts
   - 新增 returnCheckpoint / returnBannerEl / rewindBusy
   - 新增 getPiState / fetchForkMessages / syncForkEntryIds
   - 新增 reloadMessagesFromPi
   - 新增 rewindToMessage / returnToLatest
   - agent_end 后异步 syncForkEntryIds
   - sendMessage 时如果存在 returnCheckpoint 且不是 steering，则清空 returnCheckpoint

4. banner 位置
   - 放在 headerBar 下方、messages 区域上方
   - 不放在 messagesContainer 底部

5. returnCheckpoint
   - 不持久化
   - 重启后丢失是预期行为

6. get_fork_messages mismatch
   - console.warn
   - 不弹全局 Notice
   - 没有 entryId 的消息不显示 rewind 图标
```

结论：**调研结果可信，可以进入实现阶段。第一版目标应明确为 message rewind + return to latest，而不是完整 undo/redo。**
